# 하루결 개발 계획 v0.3

## 1. 단계와 종료 조건

기간은 개발 인원·실기기·배포 방식 확정 후 산정한다. 아래 순서는 작업 의존성 기준이다.

| 단계 | 작업 | 완료 증거 |
|---|---|---|
| D0: 설계 | 습관·체크인 최우선, 화면 흐름, 데이터·알림·백업 규칙 정리 | 현재 세 문서 검토, 미확정 결정 기록 |
| M1-A: 기반 | Android 프로젝트, Compose·Room·설정, 저장소·빌드 CI | debug APK 빌드, DB 초기화·재시작 유지 |
| M1-B: 습관·체크인 | 완료·수량·시간 목표와 기록량 저장, 목표 이력, 오늘 화면, 기록 달력, 달성 표시·통계 | 오프라인 생성→부분 기록→달성→초기화→과거 수정, 정밀도·재시작·동시 수정·통계 검증 |
| M1-C: 할 일 | 받은함·목록·태그·체크리스트, CRUD·완료·휴지통·검색 | 오프라인 생성→분류→완료→복구 흐름 |
| M1-D: 일정 | 날짜·시간대, 반복 계산·회차 기록, 월 캘린더 | 월말·윤년·DST·중복 완료 테스트 |
| M1-E: 알림 | 습관 알림·체크인 액션, 작업 예약·취소·완료·미루기, 권한·재부팅 복구 | 체크인·주 목표 달성·보관 후 알림 중단, 권한 거부·회차 변경·재부팅 실기기 검증 |
| M1-F: 보호·출시 | 습관·체크인 포함 백업·복원, migration, 테마·접근성, APK | 손상 파일 무변경, 교체 복원, 사용자 흐름 검증 |
| M2 | 집중·위젯·종합 통계·한국어 날짜 입력 | 각 기능 설계 보완 후 개별 수용 기준 통과 |
| M3 | 고급 보기·고급 캘린더·필터·카운트다운 | 실제 사용 요구 기준으로 우선순위 확정 |
| M4 | 여러 기기·협업·외부 연동·AI | 서버 비용·개인정보·충돌 정책·권한 설계 확정 |

D0 이후 바로 코드 구현으로 넘어가지 않는다. 설계 검토에서 M1 범위와 기본값을 확인한 뒤 구현한다.
M1은 비행기 모드에서 습관 생성·체크인·기록 수정·통계와 할 일·반복·캘린더·파일 백업이 가능할 때 완료로 판단한다.
첫 구현 검토는 습관 생성→오늘 체크인→기록 확인 흐름으로 진행한다. 할 일 구현보다 우선한다.

## 2. 검증 계획

핵심 실패 가능성에 테스트를 집중한다. UI 문구나 단순 필드 복사만 검증하는 중복 테스트는 만들지 않는다.

| 대상 | 필수 사례 |
|---|---|
| 습관·체크인 | 매일·선택 요일·주 N일, 중복 요청, 취소 재시도, 과거 수정, 미래·비대상 날짜 거부 |
| 목표 유형·수량 | CHECK 0/1, 소수 수량의 정확한 합계, 정수 분, 목표량 경계·초과량 보존, 음수·잘못된 소수·overflow 거부 |
| 기록 경쟁 | 빠른 ＋1, 중복 저장, 초기화 후 오래된 요청, 입력 화면과 알림 동시 조작, revision 충돌 시 무덮어쓰기 |
| 습관 통계 | 비대상 날짜 건너뛰기, 진행 중 오늘·주, 부분 첫 주, 기간 경계, 목표 변경 전후, 시간대 이동 |
| 습관 알림·보관 | 부분 기록 유지·목표 달성 후 취소, 목표 미달로 수정 후 재계산, 유형별 액션, 지난 날짜 액션, 보관 후 기록 유지·알림 중단 |
| 반복 계산 | 1/31→2월 말→3/31, 2/29 연 반복, 주 간격·요일, 종료일 포함, 늦은 완료 |
| 시간 | 날짜 없음·종일·시간 지정, 서울↔다른 시간대, DST gap·overlap |
| 완료·삭제 | 중복 완료, 직후 되돌리기, 오래된 알림 액션, 반복 삭제·복구 |
| Room | FK·unique 제약, 목록 삭제 시 받은함 이동, 트랜잭션 rollback, 버전 migration |
| 백업 | 정상 round trip, 습관 유형·단위·목표 이력·부분/초과 기록량·휴지통·회차 보존, 손상·초과 크기·잘못된 FK·상위 버전 거부 |
| 알림 | 허용·거부·철회, 정확한 알람 불가 시 대체, 재부팅, 미루기 재시작, 수정 후 이전 알림 차단 |
| UI·접근성 | 습관 생성→오늘 체크인→취소→기록 수정, 빠른 추가→오늘→완료, 캘린더→날짜 변경, TalkBack, 큰 글씨, 밝게·어둡게 |

실기기는 최소 지원 OS와 최신 지원 OS를 포함한다. 제조사 절전 제한이 있는 기기도 한 대 검증한다.
앱을 구현하기 전에는 빌드·기능 테스트를 수행했다고 보고하지 않는다.

## 3. 저장소·배포

- 결과물 저장소: [bossxor/tool_ScheduleMng](https://github.com/bossxor/tool_ScheduleMng).
- 현재 결과물은 설계 Markdown 문서다. 구현 단계에는 코드, 테스트, CI, 빌드 안내를 같은 저장소에 보관한다.
- 변경은 목적별 커밋으로 남긴다. 앱 코드 변경은 브랜치와 PR로 검토하며 검증 결과를 기록한다.
- CI는 구현 단계에서 debug 빌드·단위 테스트부터 시작한다. 배포 서명 키는 저장소 외부에서 관리한다.
- 초기 배포 후보는 GitHub Releases의 APK다. Play Store 출시는 별도 결정이다.

| 사용자 확정 | 이름 하루결, Android, 개인용·오프라인 우선, 습관·체크인 최우선 및 M1 필수, 완료·수량·시간 목표, 활기찬 달성 표시, 지정 GitHub 저장소 사용 |

## 5. 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 참고 서비스 전체 기능을 한 번에 구현하면 범위 증가 | 기능 목록을 보존하고 M1~M4로 나눠 순차 구현 |
| 알림이 OS·절전 정책에 제한됨 | 권한 상태 표시, 재예약, 실기기 검증, 정확성 보장 범위 안내 |
| 반복 회차·시간대 처리 오류 | 순수 날짜 계산 테스트와 DB 트랜잭션, 회차 중복 차단 |
| 수량 기록 중복·소수 오차·과거 목표 변경 | 정수량 저장·revision 비교, 날짜별 목표 이력 보존, 부분·초과 기록 테스트 |
| 앱 삭제·복원으로 데이터 손실 | 명시적 백업, 교체 확인, 내부 복구 스냅샷, migration 테스트 |
| 향후 동기화를 단순 추가로 오해 | 별도 데이터 충돌·삭제 전파·인증 설계 단계 유지 |

이번 단계에서 앱 코드, 서버, SDK 설치, APK 빌드, 실기기 테스트는 수행하지 않는다.

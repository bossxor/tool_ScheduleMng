# 하루결 개발 계획 v0.5

## 1. 단계와 종료 조건

기간은 개발 인원·실기기 확인 후 산정한다. 아래 순서는 작업 의존성 기준이며 M1은 나누지 않고 한 번에 완성한다.

| 단계 | 작업 | 완료 증거 |
|---|---|---|
| D0: 설계 | 습관·체크인 최우선, 화면 흐름, 저장·알림·백업·업데이트 규칙 정리 | 현재 세 문서 검토, 미확정 결정 기록 |
| M1-A: 기반 | 시작 조건: release 서명 키 생성. Android 프로젝트, Compose, `AppStore`(JSON 파일·원자적 쓰기·버전 변환), 빌드 CI | release 키로 서명한 APK 실기기 설치, 저장·재시작 유지, 쓰기 중 강제 종료 후 파일 온전 |
| M1-B0: 디자인 자원 | 색상·글자체(주아·Pretendard) 토큰 코드화, 습관 그림 45개·마일스톤 4개·상태 그림 7개 선정(무료 세트 우선, 없으면 AI 생성 후 선별), 앱 아이콘(해+체크), 출처 대장 | 밝은·어두운 모드 시안 확인, 그림 목록 완성·출처 대장 누락 없음, 32dp 판독, 글자 확대에서 줄바꿈 확인 |

| M1-G: 보호·출시 | 백업·복원, 스냅샷 되돌리기, 테마·접근성, 첫 릴리스 | 손상 파일 무변경, 교체 복원, 사용자 흐름 검증 |
| M2 | 집중·위젯·종합 통계·한국어 날짜 입력 | 각 기능 설계 보완 후 개별 수용 기준 통과 |
| M3 | 고급 보기·고급 캘린더·필터·카운트다운·할 일 수동 순서 | 실제 사용 요구 기준으로 우선순위 확정 |
| M4 | 여러 기기·협업·외부 연동·AI | 서버 비용·개인정보·충돌 정책·권한 설계 확정 |

D0 이후 바로 코드 구현으로 넘어가지 않는다. 설계 검토에서 M1 범위와 기본값을 확인한 뒤 구현한다.
M1은 비행기 모드에서 습관 생성·체크인·기록 수정·건너뛰기·통계와 할 일·반복·캘린더·파일 백업이 가능하고, GitHub 릴리스로 업데이트가 한 번 이상 성공할 때 완료로 판단한다.
구현 순서는 습관 생성→오늘 체크인→기록 확인 흐름을 할 일보다 먼저 진행한다.

## 3. 저장소·배포

- 결과물 저장소: [bossxor/tool_ScheduleMng](https://github.com/bossxor/tool_ScheduleMng). 자동 업데이트가 이 저장소의 공개 릴리스를 읽으므로 공개 상태를 유지한다.
- 코드, 테스트, CI, 빌드 안내를 같은 저장소에 보관한다. 변경은 목적별 커밋으로 남기고 앱 코드는 브랜치와 PR로 검토한다.
- CI는 debug 빌드·단위 테스트부터 시작한다.

**패키지 ID와 서명 키**

- 패키지 ID는 `com.bossxor.harugyeol`로 확정한다. 나중에 바꾸면 다른 앱이 되어 재설치·데이터 이전이 필요하다.
- release 서명 키를 첫 실기기 설치 전에 만든다. 키 파일과 비밀번호는 Git 밖 두 곳에 보관한다.
- 키를 잃으면 업데이트가 불가능해 앱을 지우고 다시 설치해야 한다. 데이터는 백업 파일로만 옮길 수 있다.
- 실기기에는 release 키로 서명한 APK만 설치한다. debug 서명 앱 위에는 release APK를 업데이트로 설치할 수 없다.

**릴리스 절차**

1. versionCode를 1 올리고 versionName을 새 태그와 같게 정한다(`vX.Y.Z` ↔ `X.Y.Z`).
2. release APK를 로컬에서 빌드·서명한다.
3. APK 파일명을 `Harugyeol-vX.Y.Z.apk`로 하고 `gh release create vX.Y.Z Harugyeol-vX.Y.Z.apk --notes "변경 내용"`으로 올린다. APK asset은 하나만 둔다.
4. 시험용 빌드는 사전 릴리스(`--prerelease`)로 올린다. 자동 업데이트 대상이 아니다.

- release 빌드의 CI 자동화는 서명 키를 GitHub Secrets에 올려야 하므로 M1에서는 로컬 빌드로 한다. 필요해지면 그때 옮긴다.
- 같은 패키지 ID와 서명 키를 유지하고 versionCode를 늘려 데이터 유지 업데이트를 검증한다. Play Store 출시는 M1 필수가 아니다.

## 5. 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 참고 서비스 전체 기능을 한 번에 구현하면 범위 증가 | M1 범위를 고정하고 나머지는 M2~M4로 보존 |
